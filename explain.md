# AstraNav-IDR - Repository Explanation

> [!NOTE]
> This document provides a comprehensive overview of the AstraNav-IDR repository, an offline, deterministic, and live-filter browser replay instrument developed for Team Recalibrate's **SIH 2026 Problem Statement 26168**: *AI-ML based intelligent dead reckoning for seamless navigation*.

## 1. Project Purpose & Overview

AstraNav-IDR demonstrates robust dead reckoning capabilities when GNSS (GPS) signals become degraded or denied (e.g., in urban canyons, tunnels, or under jamming). It achieves this by fusing raw IMU sensor data with machine learning predictions and physical constraints in a real-time filter running directly in the browser. 

The system relies on a **15-state Error-State Extended Kalman Filter (ES-EKF)**, aided by a **learned motion-mode virtual odometer**, **Non-Holonomic Constraints (NHC)**, **ML-gated ZUPT/ZARU**, **NIS GNSS integrity gating**, and a **Viterbi HMM route-topology matcher**. 

A key feature of this prototype is that it runs **100% offline**. All benchmark datasets (IO-VNBD), model weights, and scenario geometries are bundled locally to ensure privacy, determinism, and standalone capability.

## 2. Architecture & Data Flow

The project architecture spans from an offline Python data preparation pipeline to a live, deterministic TypeScript engine running in the browser UI.

### Data Flow Overview
1. **Offline Pipeline:** [`tools/prep_iovnbd.py`](tools/prep_iovnbd.py) ingests raw smartphone sensor captures (IO-VNBD dataset). It trains a Multinomial Logistic Regression motion-mode classifier to estimate speed classes from IMU variances and generates bundled JSONs for replay (`iovnbd-model.json`, `iovnbd-segments.json`, `iovnbd-trips.json`).
2. **Replay Engine:** When a scenario is loaded (either a bundled segment, a synthetic scenario, or a user-provided BYOD capture), the engine parses the raw sensor channels.
3. **Live Filter Execution:** The `liveeskf` engine propagates the 15-state ES-EKF at 10 Hz over the scenario duration, gating GNSS updates during simulated blackouts, and relying on the ML speed aid, ZUPT, and NHC to constrain the drift.
4. **Map Matching:** The filter's trajectory is fed into the Viterbi HMM matcher which snaps it to the expected route topology.
5. **UI Rendering:** The React frontend consumes the `Snapshot` arrays generated by the engine, displaying the traces on a simulated SVG map (`CityMap.tsx`) and rendering diagnostics and evaluation metrics across various views.

## 3. Folder Structure & Key Components

- **`src/`**: The core TypeScript/React source code.
  - **`engine/`**: The deterministic navigation and simulation core.
    - [`types.ts`](src/engine/types.ts): Central type definitions for `Snapshot`, `Run`, `Config`, `Scenario`, and estimators.
    - [`esekf.ts`](src/engine/esekf.ts): The mathematical core of the 15-state Error-State EKF. Defines propagation (`propagate`), GNSS NIS-gated updates (`updateGnss`), ML updates (`updateMlSpeed`), NHC (`updateNHC`), ZUPT (`updateZupt`), and ZARU (`updateZaru`).
    - [`liveeskf.ts`](src/engine/liveeskf.ts): The "live" runner that executes the ES-EKF over real IO-VNBD replay channels. Computes the 2σ-style covariance envelope and systematic-heading protection bounds.
    - [`iovnbd.ts`](src/engine/iovnbd.ts): Loads pre-generated JSON bundles, manages scenarios, and coordinates the execution of the `liveeskf` and map matcher to build a complete `Run`.
    - [`mapmatch.ts`](src/engine/mapmatch.ts): Implements the Viterbi algorithm for Hidden Markov Model (HMM) route-topology matching. It penalizes non-monotonic jumps and applies Gaussian emission probabilities based on distance.
    - [`byod.ts`](src/engine/byod.ts): Handles "Bring Your Own Drive" functionality, mapping raw phone motion/orientation JSON exports into the replay pipeline. It now includes `buildByodCounterfactualRun` for zero-leakage GNSS masking ("What if GPS disappeared here?") and robust sensor validation.
    - [`runlog.ts`](src/engine/runlog.ts): Manages offline `localStorage` persistence of generated runs for the "Run Library" view.
  - **`components/`**: React UI components for the web console.
    - [`App.tsx`](src/App.tsx): The main application shell. Wires navigation to the core views.
    - [`NarrationBar.tsx`](src/components/NarrationBar.tsx): Provides dedicated, state-reactive engineering narration badges (NOMINAL, DENIED, REACQUIRING, DEGRADED) and contextual explanations.
    - [`CityMap.tsx`](src/components/CityMap.tsx): The central SVG-based map rendering the different estimator trajectories (INS, Classical, EKF, Map-matched), GNSS dots, and uncertainty bounds, with dynamic ENU bounding box calculation.
    - [`ReplayLab.tsx`](src/components/ReplayLab.tsx): UI for toggling ablation settings (NHC, ZUPT, ML, Gate) and injecting synthetic faults.
    - [`Evidence.tsx`](src/components/Evidence.tsx), [`ChartsPanel.tsx`](src/components/ChartsPanel.tsx), [`ComparatorView.tsx`](src/components/ComparatorView.tsx), etc.: Analytical views for comparing performance metrics.
  - **`styles.css`**: Vanilla CSS providing the entire styling framework (tokens, responsive layouts, specific component classes). No heavy CSS frameworks like Tailwind are used.
- **`tools/`**: Offline data preparation and ML training scripts.
  - [`prep_iovnbd.py`](tools/prep_iovnbd.py): The Python script that parses raw CSVs, extracts features, trains the Logistic Regression motion model, calculates offline baselines (INS, classical EKF), and dumps the results to the `public/data/` folder.
- **`public/`**: Static assets served by Vite.
  - **`data/`**: Generated `.json` bundles (`iovnbd-model.json`, `iovnbd-segments.json`, `iovnbd-trips.json`).
  - [`favicon.svg`](public/favicon.svg): Vector SVG favicon featuring AstraNav branding.
  - [`byod.html`](public/byod.html): A standalone HTML page for capturing actual device motion and orientation data from a mobile browser to feed into the engine, hardened with a sensor watchdog and v2 schema.
- **`docs/`**: Extensive project documentation, meeting notes, styleguides, and testing checklists.


## 4. Major Execution Flows

### IO-VNBD Scenario Replay
1. **Selection:** User selects a scenario in the UI (`App.tsx`).
2. **Configuration:** `useReplay.ts` hook detects the change and calls `buildIovnbdRun` from [`iovnbd.ts`](src/engine/iovnbd.ts). All traces are strictly aligned to the exact same ENU coordinates.
3. **Execution:** `buildIovnbdRun` extracts the segment data and executes `runLiveEskf` starting from the first valid GNSS fix.
4. **Filtering:** `runLiveEskf` loops through the 10 Hz time steps. For each step:
   - Propagates error state with IMU gyro data (`propagate`).
   - Gated update: If GNSS is available and not in blackout, checks NIS (`updateGnss`).
   - If ML aiding is enabled, applies `updateMlSpeed`.
   - If physically stopped (via `zupt` mask + ML prediction), applies `updateZupt` and `updateZaru`.
   - Applies `updateNHC`.
   - Calculates uncertainty bound (`boundCov`, `boundPL`).
5. **Matching:** `buildIovnbdRun` runs the `matchTrack` Viterbi HMM over the resulting live track if map matching is enabled.
6. **Snapshots:** Assembles all internal variables per epoch into `Snapshot` objects.
7. **Playback:** UI reads `replay.snapshot` based on the current playback time (`t`) and renders the map and diagnostics, accompanied by the `NarrationBar`.

### BYOD Capture Pipeline
1. User captures real-time data using the standalone [`byod.html`](public/byod.html) page on their mobile device and saves the JSON.
2. The user uploads this JSON via the "YOUR DRIVE (BYOD)" option in the scenario modal (`App.tsx`).
3. [`byod.ts`](src/engine/byod.ts) adapts the irregular device data (DeviceMotion, DeviceOrientation, Geolocation API) into the standard 10 Hz array format. It calibrates gyro bias from the calmest window and anchors the heading to the GPS course.
4. The system executes the exact same `buildByodRun` -> `runLiveEskf` path as the benchmark dataset. Users can also trigger a **counterfactual GNSS denial** ("What if GPS disappeared here?") to inject synthetic blackouts natively into their own drives.

## 5. Important Design Decisions & Technical Details

> [!TIP]
> The engine prioritizes determinism and offline capability. It relies on standard math and linear algebra arrays rather than heavy external libraries like numeric.js or math.js.

- **15-State ES-EKF over Simple EKF:** The error-state representation separates the highly non-linear nominal state (quaternions) from the linear error propagation. It prevents singularity issues associated with Euler angles.
- **2D Dimensionally Consistent NIS Gating:** Fixes with a Normalized Innovation Squared (NIS) exceeding the $\chi^2(2, 0.99) = 9.21$ gate are rejected. This prevents wild multipath GNSS jumps (e.g. entering a tunnel) from corrupting the filter states.
- **ML-Gated ZUPT:** Standard ZUPT relies strictly on low accelerometer variance, which often triggers false stops during smooth highway cruising. AstraNav requires BOTH the physical sensor variance check AND the ML model predicting a high probability of being "stopped" to engage a hard zero-velocity update.
- **Ablation & Fault Injection:** The `liveeskf` is strictly parameterized by `Ablation` toggles (NHC, ZUPT, ML, Gate), allowing the UI (`ReplayLab.tsx`) to instantly rebuild the trajectory to demonstrate the impact of turning off constraints or injecting faults.
- **Viterbi Map-Matching:** Real-world map matching requires snapping noisy traces to road topologies. Since IO-VNBD lacks OSM graphs, a proxy 1D topology (the reference route) is used with a Viterbi HMM algorithm (`mapmatch.ts`) to demonstrate emission-distance and heading transition logic.

## 6. Configuration & Deployment

- **Dependencies:** React, ReactDOM, Lucide React (icons). Dev dependencies include Vite, TypeScript, and Vitest.
- **Build & Dev:** Managed via `package.json` scripts:
  - `npm run dev`: Starts local Vite server.
  - `npm run build`: Typechecks with `tsc -b` and builds production bundle with Vite.
  - `npm test`: Runs the Vitest test suite.
- **Environment:** No `.env` variables or server-side backends are required. All features run client-side. 
- **Tests:** The repository contains a comprehensive suite (70 tests across 8 suites) including `esekf.test.ts`, `simulation.test.ts`, `mapmatch.test.ts`, `byod.test.ts`, `export.test.ts`, and `runlog.test.ts`. This ensures mathematical zero-leakage invariance and bitwise determinism.

## 7. Known Limitations & Technical Debt

> [!WARNING]
> While the prototype is functionally complete for the hackathon presentation, several engineering constraints are intentionally maintained to reflect real-world limitations.

- **Horizontal Accelerometer Suppression:** The `liveeskf.ts` intentionally suppresses phone accelerometer propagation for horizontal velocity. Research showed smartphone IMUs (MEMS) are too noisy at 10 Hz to integrate reliably without excessive random walk. Velocity relies heavily on ML aiding, GNSS, and NHC.
- **Cross-Mount Generalization (LOTO):** As documented in `prep_iovnbd.py` and the UI's Model Inspector, the motion-mode regression struggles with cross-mount transfer (Leave-One-Trip-Out). Different phone orientations shift the sensor axes. The current ML model uses rotation-invariant features (magnitudes, signal energy) to combat this, but it remains an open challenge.
- **Synthetic Covariance Bounds:** The uncertainty bounds displayed (2σ covariance + systematic heading Protection Level) are illustrative models scaled to show growth during an outage. They do not constitute formally validated ARAIM/SBAS protection levels for life-critical applications.
- **No Native Edge Code (Yet):** The production target envisions the ES-EKF written in C++ running at 100-200 Hz on Android. The current implementation is a 10 Hz TypeScript replay proxy.

## 8. Glossary of Buzzwords & Core Concepts

- **ES-EKF (Error-State Extended Kalman Filter)**: A variant of the Kalman Filter that estimates the *error* in the state (like position, velocity, and orientation) rather than the absolute state itself. It is highly effective for handling 3D rotations (quaternions) without singularity issues.
- **Dead Reckoning (DR)**: The process of calculating the current position by using a previously determined position and advancing it based on known or estimated speeds, elapsed time, and course.
- **ZUPT (Zero Velocity Update)**: A constraint applied to the filter when the vehicle is stationary, forcing the velocity estimate to zero to prevent drift from accumulating.
- **ZARU (Zero Angular Rate Update)**: A constraint applied when stationary, forcing the rotation rate to zero to help observe and correct gyroscope bias.
- **NHC (Non-Holonomic Constraints)**: Physical constraints of wheeled vehicles, typically assuming the vehicle cannot move sideways (lateral velocity = 0) or jump into the air (vertical velocity = 0) in its own body frame.
- **GNSS (Global Navigation Satellite System)**: The standard generic term for satellite navigation systems (like GPS, GLONASS, Galileo) that provide geo-spatial positioning.
- **NIS (Normalized Innovation Squared) / $\chi^2$ Gating**: A statistical test used to reject outlier measurements (like multipath GNSS jumps when entering a tunnel). It measures how far an observation is from the prediction, normalized by their combined uncertainty.
- **Viterbi Algorithm / HMM (Hidden Markov Model)**: A dynamic programming algorithm for finding the most likely sequence of hidden states (e.g., road segments) that results in a sequence of observed events (e.g., noisy GPS/filter positions).
- **Virtual Odometer (ML Speed Aiding)**: Using machine learning to estimate forward speed based on IMU variance/energy patterns, substituting for a physical wheel speed sensor.
- **LOTO (Leave-One-Trip-Out)**: A cross-validation technique where a model is trained on all trips except one, and tested on the left-out trip, to measure generalization across different environments or phone mounts.
- **BYOD (Bring Your Own Drive)**: A feature allowing users to capture data on their own smartphones and replay it through the same navigation pipeline.
- **Counterfactual GNSS Denial**: Synthetically masking out GNSS fixes from a real-world capture to simulate an outage and test the dead-reckoning performance ("What if GPS disappeared here?").
- **Protection Level / Bound**: An integrity envelope that calculates a safe, mathematically guaranteed bound on the position error (used in aviation like SBAS), rather than just an average expected error. 
- **IMU (Inertial Measurement Unit)**: A device (inside the phone) that measures specific force, angular rate, and sometimes magnetic field, using accelerometers, gyroscopes, and magnetometers.
- **ENU (East-North-Up)**: A local tangent plane coordinate system used for navigation, where X is East, Y is North, and Z is Up.
- **OOD (Out-of-Distribution)**: Data that differs significantly from the training dataset. Used here to suspend ML predictions when the phone moves in ways the model hasn't learned.
- **Ablation**: The process of systematically turning off specific algorithmic components (like ZUPT, ML, NHC) to measure their individual impact on the overall system performance.
